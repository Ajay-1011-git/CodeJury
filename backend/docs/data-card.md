# Stage 1 synthetic corpus

Original project-authored controlled-corruption data, collected 2026-10-11. No external benchmark, API teacher, QuixBugs, EvalPlus, or purported natural student error is included. Redistribution license is not yet declared by the repository; provenance records say so explicitly.

There are 60 Stage 1 base specifications: 40 training in eight families, 10 validation in two families, and 10 internal assessment in two further families. A separate Stage 2 pool contains 10 bases in two reserved families. Counts refer to base functions, not traces or variants. Broad algorithm families and exact alpha-normalized solution fingerprints must be disjoint across splits. Within-family near duplicates share a split. This is the minimum prototype collection, not the 120-base target or evidence of broad generalization.

Each base has four independently authored examples. Two are runtime-visible; two are offline assessment cases. References execute only in the isolated runner. Return expressions are replaced with integer zero or null to create two clearly synthetic corruption variants per Stage 1 base. These are deliberately simple return bugs; they do not represent real student errors or realistic bug distributions. Both variants must fail at least one supplied visible test. Initial collection retained 80 train, 20 validation and 20 assessment records; the separate Stage 2 pool has 19 retained variants. One ineffective Stage 2 corruption was rejected rather than relabelled valid.

The seal in data/manifests/stage1.json fixes asset hashes, split provenance and counts. Validation, assessment and Stage 2 asset bytes are local and ignored; only hashes are published. The offline catalog used to author the specifications is committed for reproducibility, including construction definitions for the reserved problems. Thus the pool is sealed against experiment changes and hidden from runtime prompts, **not secret from a developer reading the offline authoring code**. This synthetic assessment is not an independent unseen benchmark. Use genuinely external or newly collected problems for the later generalization study.

The public API demo (stable unique order) is absent from the training/scored pools. Later demo additions must disclose any overlap. Data collection/validation never feeds hidden cases into prompts. SFT exports exactly runtime request fields and actual visible failure observations, followed by an assistant JSON completion containing replacement source, diagnosis and assumptions. It writes train.jsonl and valid.jsonl only; sealed assessment and Stage 2 targets cannot be exported.

Installed MLX-LM 0.32.0 ChatDataset was inspected: messages list with a final assistant completion, tokenizer.apply_chat_template, and --mask-prompt computing the offset from messages before the final assistant. Actual tokenizer/mask execution is part of A.06. Export requires a current successful live sandbox validation proof matching the sealed manifest.
